# Архитектура Lectora

Документ описывает, как устроен продукт, какие решения приняты и почему. Он рассчитан на
инженера, который будет сопровождать код, и на жюри, которому нужно понять глубину решения.

## 1. Компоненты

| Компонент | Роль | Ключевые файлы |
|---|---|---|
| SPA (React) | библиотека, плеер, транскрипт, поиск, конспект, Q&A | `frontend/src` |
| HTTP API (Flask) | REST, SSE, раздача видео и SPA | `backend/app/api` |
| Доменные сервисы | ASR, перевод/TTS, эмбеддинги, реранкер, LLM, поиск, конспект, рекомендации | `backend/app/services` |
| Шпаргалка к экзамену | слияние готовых конспектов группы одним вызовом модели + детерминированное извлечение, кэш по отпечатку | `services/exam.py` |
| Очередь задач | БД-очередь + фоновый воркер, восстановление после сбоя | `services/jobs.py` |
| Пайплайн | стадии обработки видео с прогрессом и обработкой ошибок | `services/pipeline.py` |
| PostgreSQL | источник истины: лекции, транскрипт, чанки, конспект, очередь | `models.py` |
| Локальная LLM | llama.cpp server, OpenAI-совместимый `/v1` | `tools/llama-vulkan` |
| DeepSeek API | FreeDeepseekAPI: DeepSeek Web как OpenAI-совместимый `/v1` | `tools/FreeDeepseekAPI`, `services/llm_api.py` |

Основной конвейер может работать локально. Интернет нужен для установки, импорта по ссылке,
DeepSeek-перевода/API-конспекта и edge-tts. FreeDeepseekAPI слушает `127.0.0.1`, но обращается
к DeepSeek Web. Режим `local` автономен для конспекта и Q&A; перевод в нём намеренно
запрещён, чтобы не выдавать непредсказуемый результат локальной 7B-модели.

## 2. Поток запроса

### Загрузка лекции

```
POST /api/lectures (multipart)
  → Storage.save_upload (поток, лимит MAX_UPLOAD_MB, UUID-каталог)
  → INSERT lectures(status=queued) + INSERT jobs(status=queued)
  → 202 Accepted {lecture, job_id}
```

Для импорта по ссылке (`POST /api/lectures/import`) лекция создаётся без файла, а воркер
первой стадией скачивает видео через yt-dlp в каталог лекции и продолжает общий пайплайн.

Файл не буферизуется в памяти: чтение идёт блоками по 1 МБ, при превышении лимита файл
удаляется и возвращается 413. Загрузка идёт с прогрессом на клиенте (XHR).

### Обработка

```
worker: SELECT ... FOR UPDATE SKIP LOCKED (jobs where status=queued)
  → pipeline.process(lecture_id, job_id)
  → стадии, каждая пишет stage/progress в lectures и jobs
  → ready | failed + error_message
```

Воркер — один поток на процесс (`WORKER_THREADS`), потому что ASR и так упирается в CPU.
`SKIP LOCKED` позволяет безопасно запускать несколько процессов, не дублируя задачи.

Языковой участок пайплайна:

```
audio → Whisper/Vosk → transcript_segments.text
                       └─(target_language + llm_mode=api)─► DeepSeek batch translation
                                                          ├─► translated_text
                                                          └─(voiceover)─► edge-tts parts
                                                                               └─► FFmpeg MP3
```

Перевод выполняется батчами без слияния сегментов, поэтому исходные таймкоды остаются
валидными для обоих языков. Русский голос — `ru-RU-SvetlanaNeural`, английский —
`en-US-AriaNeural`.

### Прогресс

`GET /api/lectures/{id}/events` — SSE. Генератор раз в 0.9 с читает состояние лекции,
отдаёт событие только при изменении и закрывает поток на `ready`/`failed`. Это не требует
pub/sub и переживает перезапуск клиента.

### Поиск

```
query → atoms (C++, C#, .NET) → encode (bge-m3, кэш)
      → dense (numpy, кэш матрицы) + lexical (PostgreSQL FTS)
      → exact-term coverage (IDF, текст и название лекции)
      → fusion → rerank top-K (окно вокруг совпадения) → порог → dedupe → JSON
```

* Матрица эмбеддингов лекции кэшируется в памяти процесса и инвалидируется по версии
  `(processed_at, chunk_count)`.
* Dense-скоры калибруются z-скорингом по корпусу: min-max делал лучший фрагмент «единицей»
  даже когда запрос не совпал ни с чем.
* Технические термины (`C++`, `C#`, `.NET`) нельзя искать ни FTS (теряет `+`/`#`/`.`), ни
  эмбеддингами (C++ и Java близки по смыслу). Они сопоставляются регулярным выражением с
  алиасами распознавания («си плюс плюс»), взвешиваются по IDF и проверяются в названии
  лекции; чанк без запрошенного термина не может попасть в топ. Запрос без совпадений
  возвращает пустую выдачу.
* Реранкер вызывается только для топ-6 кандидатов и кэшируется по `(query, chunk_ids)` —
  повторный запрос отвечает за ~20 мс. Ему отдаётся окно текста вокруг найденного слова,
  а не первые 420 символов чанка.
* Дедупликация убирает соседние фрагменты одной лекции (окно 12 с), чтобы выдача не
  состояла из трёх перекрывающихся кусков.

### Q&A

```
question → поиск по лекции (top-6) → промпт с [таймкод] фрагментами → LLM → ответ + цитаты
```

Бэкенд ответа выбирается по `lecture.llm_mode`: DeepSeek API даёт развёрнутый ответ (4–8
предложений), локальная модель — короткий. Если выбранный бэкенд недоступен, цепочка
`api → local → offline` деградирует до подборки фрагментов с `llm_used=false`. Вопросы и
ответы сохраняются в `qa_messages` и переиспользуются в интерфейсе.

### Рекомендации

```
готовые лекции пользователя ─┐
                             ├─► TopicCandidate → взвешенные точки интереса
первые просмотры публичных ──┘        (subject / topic / keyword)
                                        │
публичный каталог ─► кандидаты ─► скоринг по совпадению тем ─► popular/fresh добор
                                        │
                                   «Для Вас»
```

* **Профиль материализован** в `user_interests`: `services/recommendations.py` пересобирает
  его целиком после готовой лекции, правки/удаления и первого просмотра. Таблица — кэш,
  поэтому не нужны хрупкие инкрементальные обновления.
* **Сигналы:** собственная готовая лекция — сильный (subject 5.0, topic 3.5, keyword 0.9),
  первый просмотр чужой публичной — слабый (2.0 / 1.5 / 0.35). Вес точки ограничен, чтобы
  один курс не вытеснил остальные интересы.
* **Сопоставление устойчиво к морфологии:** темы режутся на токены, стоп-слова
  отбрасываются, токены усекаются до 6 символов; совпадение — подмножество токенов.
  Поэтому «Функторы в C++» находит «функторы C++», а «Программирование» совместимо с
  «Программирование на C++».
* **Скоринг:** topic×3.0, subject×2.0, keyword×1.0, cross subject↔topic×1.5,
  keyword↔subject/topic×0.6; популярность и свежесть — тай-брейкеры.
* **Холодный старт:** без сигналов лента собирается по популярности и свежести
  (`mode=cold_start`). Если совпадений меньше четырёх, добавляются популярные видео с
  `personalized=false`, чтобы лента не выглядела пустой.
* **Свои лекции исключены** из выдачи. Персональные карточки идут первыми, ограничение —
  `CANDIDATE_LIMIT=300` в SQL-выборке.

### Режимы конспекта (`api` / `local`)

Селектор один — `services/llm_modes.py`. Он валидирует режим, знает цепочку деградации и
отдаёт нужный клиент:

| Режим | Клиент | Конспект |
|---|---|---|
| `api` | `ApiLlmClient` (`services/llm_api.py`) | 4 прохода, подробные разделы |
| `local` | `LlmClient` (`services/llm.py`) | один reduce-вызов в окно 8K |

Деградация намеренно консервативная: `api → local → offline`, `local → offline`, где
`offline` — не выбираемый режим, а детерминированный экстрактивный алгоритм без модели.
Выбор локального режима никогда не отправляет лекцию в облако.
Фактически использованный режим пишется в `lectures.llm_mode_used`, поэтому UI честно
показывает подмену.

**API-пайплайн конспекта** (`summarizer._api_notes`):

```
transcript ──(> API_LLM_MAX_INPUT_CHARS)──► map-окна ─► тезисы с таймкодами
     │
     └─► outline: 6–14 разделов с таймкодами
             └─► details: батчи по 1–3 раздела (summary + 4–6 тезисов + markdown)
                     └─► overview: обзор 180–300 слов, 14–20 терминов, 5–8 вопросов
                             └─► _validate: границы таймкодов, объём, дедуп, фолбэки
```

* Каждый батч ограничен `API_LLM_DETAILS_BATCH_CHARS`; при сбое батча раздел собирается
  экстрактивно из своих сегментов, поэтому один плохой ответ не обнуляет конспект.
* Map-фаза включается только для длинных записей; число окон ограничено
  `API_LLM_MAX_MAP_WINDOWS`, окно расширяется так, чтобы покрыть всю лекцию.
* `_validate` одинаково проверяет все режимы: сортирует разделы, убирает перекрытия,
  привязывает конец к длительности, гарантирует минимальный объём обзора и списки.

**Почему API-клиент такой осторожный.** FreeDeepseekAPI управляет веб-аккаунтом DeepSeek:
один ответ на чат, общие лимиты, кулдауны аккаунта, жёсткий лимит промпта. Поэтому
`ApiLlmClient`:

* сериализует запросы (`API_LLM_MAX_CONCURRENT`, по умолчанию 1) и выдерживает
  `API_LLM_MIN_INTERVAL_SEC` между стартами;
* повторяет только временные ошибки (`429`, `5xx`, сеть) с экспоненциальной паузой и
  `Retry-After`, а `401/403/400` отдаёт сразу;
* проверяет размер промпта до отправки и возвращает `kind="context"` вместо тихой обрезки;
* даёт каждому запросу одноразовый `user`-ключ сессии и сбрасывает чат через
  `/reset-session` — лекции не смешиваются, память прокси не растёт;
* берёт здоровье из `/health` (готовность аккаунтов), а не только из `/v1/models`.

## 3. Модель данных

| Таблица | Назначение | Особенности |
|---|---|---|
| `lectures` | карточка лекции, статус, метрики | UUID PK, язык/перевод/озвучка, видимость/группа, режим LLM |
| `transcript_segments` | субтитры | `idx`, `start_sec/end_sec`, `text`, `translated_text`, слова с таймингами JSONB |
| `chunks` | единицы поиска | `embedding` BYTEA (float32), `dim`, `token_count` |
| `sections` | структура лекции | заголовок, интервал, тезисы, `details` (markdown) |
| `jobs` | очередь | статус, попытки, стадия, прогресс |
| `qa_messages` | история Q&A | роль, текст, цитаты JSONB |
| `search_logs` | аналитика | запрос, scope, латентность, reranked |
| `user_interests` | профиль «Для Вас» | `(user_id, kind, topic_key)` уникален, вес и человекочитаемый label; пересобирается из лекций и просмотров |
| `lecture_views` | история просмотров | `(user_id, lecture_id)` уникален, `view_count`, первое/последнее открытие |

Индексы: `chunks_lecture_idx`, GIN по `to_tsvector('russian', text)` (создаётся в
`schema.py`), индексы по статусам и датам.

## 4. Состояния лекции

```
queued → processing → ready
              ↓
            failed
```

* `queued` — задача в очереди.
* `processing` — идёт пайплайн, есть `stage` и `progress`.
* `ready` — доступны видео, транскрипт, поиск, конспект.
* `failed` — `error_message` с человеческим объяснением; доступна кнопка «Переобработать».

При старте приложения `recover()` переводит `running`-задачи обратно в `queued` и схлопывает
дубли, поэтому убийство процесса не оставляет «вечную обработку».

## 5. Надёжность

* Ошибки внешних инструментов (ffmpeg, Vosk, LLM) оборачиваются в `ApiError` с понятным
  текстом и сохраняются в `error_message`; UI показывает их, а не «что-то пошло не так».
* Каждая стадия проверяет предусловия: есть ли аудиодорожка, распозналась ли речь,
  получились ли чанки.
* Прогресс пишется с троттлингом, чтобы не забивать БД на длинных лекциях.
* Транскрипт и чанки заменяются в одной транзакции, старые данные не теряются до успеха.
* Реранкер и эмбеддинги деградируют мягко: при ошибке поиск продолжает работать по
  плотному и лексическому скорингу.
* API-конспект пишется только после успешной валидации; при падении посреди работы
  включается локальная модель, затем офлайн-алгоритм. Старый конспект не удаляется, пока
  новый не собран.
* Задача `kind=notes` пересобирает конспект по сохранённым сегментам: транскрипт, чанки и
  история Q&A не затрагиваются, поэтому переключение режимов безопасно и быстро.
* GPU-ускорение деградирует по компонентам: `setup.ps1` ставит CUDA-сборку PyTorch только
  при совместимом драйвере, Whisper при недоступной CUDA переходит на CPU, NVENC проверяется
  реальным тестовым кадром, а при любой ошибке транскод и эмбеддинги продолжаются на CPU.
* Озвучка режется по предложениям на части до 1600 символов. Для каждой части выполняются
  три попытки с паузой; готовые MP3 остаются в кэше после сбоя и используются при повторном
  запуске. FFmpeg атомарно собирает итоговый файл, после чего временный каталог удаляется.

## 6. Производительность

| Решение | Причина |
|---|---|
| Whisper и BGE на CUDA, локальная LLM опционально на Vulkan | API-режим освобождает VRAM; локальный режим сохраняет автономность |
| Кэш матрицы чанков | поиск не читает эмбеддинги из БД каждый раз |
| Кэш реранка | повторные запросы мгновенные, демо стабильно |
| Реранк только топ-6 | 30 кандидатов на CPU стоили ~7 с, 6 — ~1,9 с |
| `max_length=256`, обрезка пассажа | cross-encoder не тратит время на хвост чанка |
| Чанки ~1 КБ, 60 с | компромисс между точностью эмбеддинга и полнотой контекста |
| SSE вместо websocket | проще, работает через waitress, без состояния |

## 7. Безопасность

* Нет загрузки исполняемых файлов: расширение проверяется по белому списку, файл получает
  UUID-имя, путь пересчитывается и проверяется на выход за `storage/`.
* `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`.
* Лимит размера загрузки и `statement_timeout` на уровне соединения с БД.
* LLM и эмбеддинги не принимают произвольный код; промпты ограничены контекстом лекции,
  модель инструктирована не выдумывать факты.
* Аутентификация — cookie-сессия с подписанной `HttpOnly`, `SameSite=Lax` cookie;
  пароли хранятся как `werkzeug`-хеши. Приватные маршруты (`/lectures`, `/groups`,
  `/recommendations`) требуют сессию, публичные (`/public`, `/shared`) работают для гостей.
* Доступ к чужой лекции проверяется по `user_id`/`group.owner_id`; рекомендации строятся
  только по публичному каталогу и никогда не раскрывают приватные видео.
* Для выхода в интернет рекомендуется reverse-proxy с TLS и ограничением частоты запросов.

## 8. Осознанные компромиссы

1. **Vosk вместо Whisper.** Требование кейса и полностью офлайн-запуск на CPU. Минус —
   нет пунктуации и хуже формулы; плюс — предсказуемое время и отсутствие тяжёлых зависимостей.
2. **Эмбеддинги в BYTEA, а не pgvector.** На масштабе курса (тысячи чанков) numpy-поиск
   быстрее и проще; pgvector добавлен в план развития.
3. **In-process воркер.** Для одного узла это минимум движущихся частей; очередь в БД
   позволяет вынести воркер в отдельный процесс без переписывания кода.
4. **Своя CSS-система вместо UI-фреймворка.** Меньше веса, полный контроль над типографикой
   и тёмной темой, нет конфликтов версий.
5. **Конспект с экстрактивным фолбэком.** Локальная 7B-модель не всегда доступна; продукт
   обязан работать и без неё, поэтому структура и обзор строятся и детерминированно.
6. **API-конспект медленнее, но подробнее.** Веб-аккаунт DeepSeek нельзя нагружать
   параллельно, поэтому 6–14 разделов собираются последовательными батчами за 30–120 с.
   Взамен получаем объём и качество, недостижимые для 7B в окне 8K.
7. **Внешний прокси, а не SDK DeepSeek.** Официальный API требует ключа и оплаты, а
   FreeDeepseekAPI повторяет приватный веб-контракт. Клиент изолирован интерфейсом
   `OpenAiCompatClient`, поэтому замена на официальный API — это смена URL и ключа.
