# Архитектура Lectora

Документ описывает, как устроен продукт, какие решения приняты и почему. Он рассчитан на
инженера, который будет сопровождать код, и на жюри, которому нужно понять глубину решения.

## 1. Компоненты

| Компонент | Роль | Ключевые файлы |
|---|---|---|
| SPA (React) | библиотека, плеер, транскрипт, поиск, конспект, Q&A | `frontend/src` |
| HTTP API (Flask) | REST, SSE, раздача видео и SPA | `backend/app/api` |
| Доменные сервисы | ASR, эмбеддинги, реранкер, LLM, поиск, конспект | `backend/app/services` |
| Очередь задач | БД-очередь + фоновый воркер, восстановление после сбоя | `services/jobs.py` |
| Пайплайн | стадии обработки видео с прогрессом и обработкой ошибок | `services/pipeline.py` |
| PostgreSQL | источник истины: лекции, транскрипт, чанки, конспект, очередь | `models.py` |
| Локальная LLM | llama.cpp server, OpenAI-совместимый `/v1` | `tools/llama-vulkan` |

Внешних сервисов нет: всё общается по `127.0.0.1`, интернет нужен только на этапе установки
моделей (и опционально для импорта по ссылке через yt-dlp).

## 2. Поток запроса

### Загрузка лекции

```
POST /api/lectures (multipart)
  → Storage.save_upload (поток, лимит MAX_UPLOAD_MB, UUID-каталог)
  → INSERT lectures(status=queued) + INSERT jobs(status=queued)
  → 202 Accepted {lecture, job_id}
```

Файл не буферизуется в памяти: чтение идёт блоками по 1 МБ, при превышении лимита файл
удаляется и возвращается 413. Загрузка идёт с прогрессом на клиенте (XHR).

### Обработка

```
worker: SELECT ... FOR UPDATE SKIP LOCKED (jobs where status=queued)
  → pipeline.process(lecture_id, job_id)
  → стадии, каждая пишет stage/progress в lectures и jobs
  → ready | failed + error_message
```

Воркер — один поток на процесс (`WORKER_THREADS`), потому что ASR и так упирается в CPU.
`SKIP LOCKED` позволяет безопасно запускать несколько процессов, не дублируя задачи.

### Прогресс

`GET /api/lectures/{id}/events` — SSE. Генератор раз в 0.9 с читает состояние лекции,
отдаёт событие только при изменении и закрывает поток на `ready`/`failed`. Это не требует
pub/sub и переживает перезапуск клиента.

### Поиск

```
query → encode (bge-m3, кэш) → dense scores (numpy, кэш матрицы чанков)
      → lexical scores (PostgreSQL FTS) → fusion → rerank top-K → dedupe → JSON
```

* Матрица эмбеддингов лекции кэшируется в памяти процесса и инвалидируется по версии
  `(processed_at, chunk_count)`.
* Реранкер вызывается только для топ-6 кандидатов и кэшируется по `(query, chunk_ids)` —
  повторный запрос отвечает за ~20 мс.
* Дедупликация убирает соседние фрагменты одной лекции (окно 12 с), чтобы выдача не
  состояла из трёх перекрывающихся кусков.

### Q&A

```
question → поиск по лекции (top-6) → промпт с [таймкод] фрагментами → LLM → ответ + цитаты
```

Если LLM недоступна, возвращаются фрагменты с пометкой `llm_used=false`. Вопросы и ответы
сохраняются в `qa_messages` и переиспользуются в интерфейсе.

## 3. Модель данных

| Таблица | Назначение | Особенности |
|---|---|---|
| `lectures` | карточка лекции, статус, метрики | UUID, статусный автомат, `keywords` JSONB |
| `transcript_segments` | субтитры | `idx`, `start_sec/end_sec`, слова с таймингами в JSONB |
| `chunks` | единицы поиска | `embedding` BYTEA (float32), `dim`, `token_count` |
| `sections` | структура лекции | заголовок, интервал, тезисы |
| `jobs` | очередь | статус, попытки, стадия, прогресс |
| `qa_messages` | история Q&A | роль, текст, цитаты JSONB |
| `search_logs` | аналитика | запрос, scope, латентность, reranked |

Индексы: `chunks_lecture_idx`, GIN по `to_tsvector('russian', text)` (создаётся в
`schema.py`), индексы по статусам и датам.

## 4. Состояния лекции

```
queued → processing → ready
              ↓
            failed
```

* `queued` — задача в очереди.
* `processing` — идёт пайплайн, есть `stage` и `progress`.
* `ready` — доступны видео, транскрипт, поиск, конспект.
* `failed` — `error_message` с человеческим объяснением; доступна кнопка «Переобработать».

При старте приложения `recover()` переводит `running`-задачи обратно в `queued` и схлопывает
дубли, поэтому убийство процесса не оставляет «вечную обработку».

## 5. Надёжность

* Ошибки внешних инструментов (ffmpeg, Vosk, LLM) оборачиваются в `ApiError` с понятным
  текстом и сохраняются в `error_message`; UI показывает их, а не «что-то пошло не так».
* Каждая стадия проверяет предусловия: есть ли аудиодорожка, распозналась ли речь,
  получились ли чанки.
* Прогресс пишется с троттлингом, чтобы не забивать БД на длинных лекциях.
* Транскрипт и чанки заменяются в одной транзакции, старые данные не теряются до успеха.
* Реранкер и эмбеддинги деградируют мягко: при ошибке поиск продолжает работать по
  плотному и лексическому скорингу.

## 6. Производительность

| Решение | Причина |
|---|---|
| Модели на CPU, LLM на GPU | 7B в VRAM, а эмбеддинги/реранкер не конкурируют за 8 ГБ |
| Кэш матрицы чанков | поиск не читает эмбеддинги из БД каждый раз |
| Кэш реранка | повторные запросы мгновенные, демо стабильно |
| Реранк только топ-6 | 30 кандидатов на CPU стоили ~7 с, 6 — ~1,9 с |
| `max_length=256`, обрезка пассажа | cross-encoder не тратит время на хвост чанка |
| Чанки ~1 КБ, 60 с | компромисс между точностью эмбеддинга и полнотой контекста |
| SSE вместо websocket | проще, работает через waitress, без состояния |

## 7. Безопасность

* Нет загрузки исполняемых файлов: расширение проверяется по белому списку, файл получает
  UUID-имя, путь пересчитывается и проверяется на выход за `storage/`.
* `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`.
* Лимит размера загрузки и `statement_timeout` на уровне соединения с БД.
* LLM и эмбеддинги не принимают произвольный код; промпты ограничены контекстом лекции,
  модель инструктирована не выдумывать факты.
* Аутентификации нет: сервис рассчитан на локальный запуск. Для публикации достаточно
  добавить reverse-proxy с авторизацией.

## 8. Осознанные компромиссы

1. **Vosk вместо Whisper.** Требование кейса и полностью офлайн-запуск на CPU. Минус —
   нет пунктуации и хуже формулы; плюс — предсказуемое время и отсутствие тяжёлых зависимостей.
2. **Эмбеддинги в BYTEA, а не pgvector.** На масштабе курса (тысячи чанков) numpy-поиск
   быстрее и проще; pgvector добавлен в план развития.
3. **In-process воркер.** Для одного узла это минимум движущихся частей; очередь в БД
   позволяет вынести воркер в отдельный процесс без переписывания кода.
4. **Своя CSS-система вместо UI-фреймворка.** Меньше веса, полный контроль над типографикой
   и тёмной темой, нет конфликтов версий.
5. **Конспект с экстрактивным фолбэком.** Локальная 7B-модель не всегда доступна; продукт
   обязан работать и без неё, поэтому структура и обзор строятся и детерминированно.
